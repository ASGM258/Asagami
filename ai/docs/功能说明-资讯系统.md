# 资讯系统功能说明

## 📖 概述

资讯系统负责把外部动漫新闻自动变成站内可阅读的中文资讯，包含**四个 LangGraph 智能体**组成的流水线，以及面向前端的查询接口。

```
AniNewsAPI / RSS
        │
        ▼
┌───────────────┐   ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│  抓取 agent    │──►│  翻译 agent    │──►│  摘要 agent    │──►│  审核 agent    │
│  归一化来源数据 │   │  英文 → 中文   │   │  摘要+去敏感   │   │  判定可否发布  │
└───────────────┘   └───────────────┘   └───────┬───────┘   └───────┬───────┘
                                                ▲                   │
                                                │  未通过且 <3 次    │
                                                └───────────────────┘
                                                    未通过且 ≥3 次
                                                            ▼
                                                  status = rejected（记录原因）
```

## ✨ 核心特性

| 特性 | 说明 |
|------|------|
| 多源抓取 | AniNewsAPI 为主源，不可用时自动降级到可配置的 RSS 源 |
| 结构容错 | 主源字段名变化时由别名映射兼容，无需改代码 |
| 中文呈现 | 翻译 agent 负责英文→中文，已是中文的内容跳过翻译 |
| 敏感信息去除 | 摘要 agent 同时清理邮箱、手机号、证件号、卡号、密钥与外部链接 |
| 质检重做 | 审核不通过自动回退摘要重做，最多 3 次 |
| 去重入库 | 按 `source_uid` 唯一索引去重，重复抓取不会产生多条记录 |
| 自动关联 | 命中 `anime` 表时自动建立 `related_anime_id` 关联 |
| 定时抓取 | 可选 cron 定时任务，默认关闭 |

## 🤖 四个智能体

### 1. 抓取 agent（`fetch`）

- 调用 AniNewsAPI，兼容「顶层数组 / `data` / `items` / `news` / `results`」等多种结构
- 字段别名映射：`headline→title`、`image_url→cover_image`、`publishedAt→publish_time` 等
- 清洗 HTML 标签与实体、归一化时间为 `YYYY-MM-DD HH:MM:SS`
- 生成去重标识 `source_uid`：优先用来源 `guid`，缺失时取 `md5(url|title|时间)`
- 主源无结果时自动降级到备用 RSS 源
- **正文补全**：RSS 只给摘要且在词中间截断，抓到的新条目会回到详情页抓全文（见下节）

#### 正文补全（`enrich`）

实测两个 RSS 源提供的正文都残缺：

| 源 | RSS 提供的正文字数 | 特征 |
|----|--------------------|------|
| MyAnimeList news RSS | 约 495 字 | 结尾是 `...episode d...` 这种残句 |
| Anime Corner feed | 约 100 字 | 只有 `description`，无 `content:encoded` |

因此抓取后会逐条访问 `source_url` 抽取正文：

1. 判定是否需要补全：正文短于 `NEWS_ENRICH_MIN_CHARS`（默认 600）**或**以省略号结尾
2. `app/news/extractor.py` 按站点规则定位正文容器（站点规则优先，通用规则兜底），
   多个候选容器取**文本最长**者，避免抓到侧栏/相关阅读
3. 只有抽取结果明显更完整时才替换原文（≥100 字且比原文多出 80 字或 20% 以上），
   防止用页脚文本覆盖原文
4. 限流按**请求次数**计（`NEWS_ENRICH_LIMIT`，默认 20 条/轮），
   请求间隔 `NEWS_ENRICH_DELAY`（默认 0.3 秒）
5. 只对**已适配站点**发请求（目前 MyAnimeList / Anime Corner）；
   新增源时在 `extractor.SITE_RULES` 补一条规则即可

补全效果实测：MyAnimeList 条目正文 495 字 → 1822 字，含完整的 Staff / Synopsis 段落。

### 2. 翻译 agent（`translate`）

- 英文资讯翻译为简体中文，动漫作品名/角色名/公司名保留原文或通用译名
- 已是中文的条目直接跳过，避免无谓的模型调用
- 输出 JSON（`{title, content}`），解析失败时保留原文交由审核判断
- **输出预算**：整篇正文要一起输出，故翻译节点使用 `NEWS_LLM_MAX_TOKENS`
  （默认 4000）而非聊天用的 1000 —— 1000 tokens 会把长文译文在中间截断
- **输入上限**：`NEWS_TRANSLATE_INPUT_LIMIT`（默认 12000 字符），
  超出时按句子边界截断，避免超出模型窗口

### 3. 摘要 agent（`summarize`）

- 生成不超过 160 字的摘要，概括作品名、时间、阵容、事件
- **去除敏感信息**：邮箱、手机号、证件号、银行卡号、API 密钥、外部链接
  - 模型负责语义清洗，另有正则兜底（`sanitize_text`），双保险
- 若带有上一轮审核反馈（`review_feedback`），按反馈针对性重做
- 每次执行都会 `attempts += 1`

### 4. 审核 agent（`review`）

审核四项标准：

1. 内容与动漫/漫画/番剧/ACG 相关（游戏、声优、活动、周边也算）
2. 中文完整通顺，标题与正文非空、无翻译残缺或乱码
3. 不含敏感信息与广告垃圾内容
4. 摘要能概括正文要点

判定结果与路由：

| 结果 | 处理 |
|------|------|
| 通过 | `stage = approved` → 落库 `status = published` |
| 不通过且 `attempts < 3` | 携带原因回退到摘要 agent 重做 |
| 不通过且 `attempts >= 3` | `stage = rejected` → 落库 `status = rejected` 并记录原因 |

模型未按 JSON 格式返回、或本地兜底校验（标题/摘要为空、仍有敏感信息）未通过时，一律按**不通过**处理，避免有问题的内容被发布。

### 工作流拓扑：线性编排，不用 `Send` 扇出

```
fetch ──► translate ──► summarize ──► review ──┬──► finalize ──► END
                          ▲                    │
                          └────────────────────┘   未通过且未达上限 → 重做
```

**踩过的坑**：早先为「让每个条目独立流转」而用了 LangGraph 的 `Send` 扇出。
但 `Send` 会让下游节点**与其后的路由函数各执行一次**（N 个条目 = N 次路由），
而路由函数读到的是「部分合并」的全局状态，于是出现：

- 已经 `approved` 的条目在另一次路由调用里又被看成 `summarized`，被拉回去重做
- `attempts` 被重复累加，**本该 1 轮通过的条目也被刷满 3 轮**
- `news_review_log` 的轨迹与实际轮次对不上（3 轮却只留 1 条记录）

改用线性编排后，每个节点自行遍历条目、只处理自己负责的阶段，
每个超步只做**一次**路由判断。节点本来就是逐条串行调模型，
去掉扇出没有损失任何并行度。回归测试见 `tests/test_news_routing.py`。

## 🗄️ 数据库设计

### news（资讯主表）

| 字段 | 说明 |
|------|------|
| `id` | 主键，前端 `NewsItem.id` |
| `title` | 标题（中文） |
| `summary` | 摘要（列表页展示） |
| `content` | 正文 |
| `cover_image` | 封面图 URL |
| `category` | 分类：动画/漫画/声优/游戏/活动 |
| `source` / `author` | 来源与发布者 |
| `publish_time` | 发布时间 |
| `tags` | 标签，英文逗号分隔 |
| `view_count` | 阅读量 |
| `source_url` / `source_uid` | 原文链接 / 去重标识（唯一索引） |
| `status` | `published` 已发布 / `rejected` 审核未通过 |
| `review_attempts` | 审核尝试次数 |
| `review_reason` | 最近一次审核意见（不通过原因） |
| `related_anime_id` / `related_anime_title` | 关联动漫（命中时才有值） |

### news_review_log（审核轨迹）

记录每次审核的 `attempt` / `passed` / `reason`，便于排查某条资讯为何被拒。

### 初始化

```bash
psql -U postgres -c "CREATE DATABASE anime_ai;"   # 会话/检查点用
mysql -u root -p backend_asagami < init_news.sql  # 资讯表
```

表结构也会在服务启动时幂等创建（`NewsService.ensure_schema()`）。

## 🔌 API接口

资讯接口挂在 **Python 服务**（默认 `http://localhost:5000/api`），与前端 `src/api/news.ts` 对应。

### 1. 获取资讯列表

`GET /api/news/list?pageNum=1&pageSize=10&category=动画&keyword=关键词`

```json
{
  "success": true,
  "message": "获取资讯列表成功",
  "timestamp": 1791458522.92,
  "data": {
    "total": 42,
    "pages": 5,
    "pageNum": 1,
    "pageSize": 10,
    "list": [
      {
        "id": 1,
        "title": "《雨夜之月》第一弹正式PV公开",
        "coverImage": "https://img/a.jpg",
        "summary": "由くずしろ原作改编的TV动画……",
        "category": "动画",
        "source": "AniNewsAPI",
        "author": "编辑部",
        "publishTime": "2026-10-08T12:58:00",
        "tags": ["PV", "配音阵容"],
        "viewCount": 0
      }
    ]
  }
}
```

> `data` 结构与前端 `PageResponse<NewsItem>` 完全一致；`list` 是本接口的键名，不是 `items`。

### 2. 获取资讯详情

`POST /api/news/detail`，请求体 `{"newsId": 1}`

在列表项字段基础上追加：

| 字段 | 说明 |
|------|------|
| `content` | 正文 |
| `relatedAnimeId` | 关联动漫ID（可空） |
| `relatedAnimeTitle` | 关联动漫标题（可空） |

资讯不存在时返回 `404` / `NEWS_NOT_FOUND`。

### 3. 获取分类列表

`GET /api/news/categories`

```json
{
  "success": true,
  "data": [
    { "key": "", "name": "全部", "count": 42 },
    { "key": "动画", "name": "动画", "count": 30 },
    { "key": "漫画", "name": "漫画", "count": 12 }
  ]
}
```

「全部」始终位于第一位，前端据此渲染筛选标签。

### 4. 手动触发抓取

`POST /api/news/refresh?limit=10&repair=true`

| 参数 | 说明 |
|------|------|
| `limit` | 本次抓取条数上限（1-100，缺省取配置） |
| `repair` | 同时修复已入库但正文残缺的条目（见下） |

工作流耗时较长（抓取 + 正文补全 + 多次模型调用），因此异步执行，接口立即返回：

```json
{
  "success": true,
  "message": "已触发资讯抓取",
  "data": { "accepted": true, "message": "资讯抓取任务已受理（含正文修复），正在后台执行" }
}
```

已有任务在执行时返回 `accepted: false`（同一时刻只允许一个工作流）。

### 5. 查询抓取状态

`GET /api/news/refresh/status`

```json
{
  "success": true,
  "data": {
    "running": false,
    "startedAt": "2026-10-19 20:15:03",
    "finishedAt": "2026-10-19 20:15:39",
    "lastRun": { "published": 2, "rejected": 0, "repaired": 0, "repairChecked": 0 }
  }
}
```

前端点「刷新」后轮询本接口，等 `running=false` 再拉列表 —— 否则一次抓取要几十秒，
用户会以为按钮没反应。

#### 正文修复（`repair=true`）

正文补全功能上线前入库的条目，正文只是 RSS 摘要（200~400 字），内容被截断。
这些条目也**大多已经掉出当前 feed**，靠"重新抓取"碰不到，因此修复走两条路径：

1. **feed 内**：抓取节点把「已入库 + 正文短 + 未补全」的条目重新送入流水线
2. **按库驱动**：`NewsService.repair_truncated()` 直接查 `news` 表里正文过短的记录，
   逐条回源抓全文 → **强制翻译** → 重新摘要 → 重新审核 → `upsert` 覆盖

> 强制翻译是必须的：修复时标题已是中文、正文却是英文摘要，
> 按「含中文就跳过翻译」的规则会漏翻。

**幂等性**：修复成功会给 `news.content_enriched` 置 1，两个查询都带
`IFNULL(content_enriched,0)=0` 条件 —— 否则像「某漫画完结」这类**源文章本身就很短**的资讯
会永远满足「< 600 字」，每轮重复烧 3 次模型调用。
老库启动时由 `ensure_schema()` 自动补这一列。

## ⏰ 定时抓取

```bash
NEWS_SCHEDULER_ENABLED=True
NEWS_SCHEDULER_CRON=0 6 * * *   # 每天 6 点
```

基于 APScheduler 的 `BackgroundScheduler`，与 FastAPI 同一进程启动；
配置 `max_instances=1` 避免上一轮未结束就重复触发，`coalesce=True` 合并错过的执行。

## 🔗 前端对接

前端资讯接口已切换到 Python 服务，其余接口仍走 Java 后端：

```ts
// src/api/news.ts
const PYTHON_API_URL = import.meta.env.VITE_PYTHON_API_URL || 'http://localhost:5000/api'
```

前端调用方式无需改动（`getNewsList` / `getNewsDetail` / `getNewsCategories` 签名与返回类型不变）：

```ts
import { getNewsList } from '@/api/news'
const res = await getNewsList({ pageNum: 1, pageSize: 10, category: '动画' })
if (res.code === 200 && res.data) {
  // 无限滚动兼容 list 与 records 两种字段名
  const list = (res.data as any).list || (res.data as any).records || []
}
```

**注意事项**

1. `publishTime` 输出 ISO 形式（`2026-10-08T12:58:00`）。前端 `formatDateTime` 用 `new Date(time)` 解析，空格分隔形式在 WebKit 下不可靠，ISO 最稳。
2. Python 服务的响应外壳是 `{success, message, timestamp, data}`，由 `news.ts` 内转换为 `{code, message, data, timestamp}`；失败时 `code` 由错误码字符串映射（`NEWS_NOT_FOUND → 404` 等）。
3. 前端 `VITE_PYTHON_API_URL` 已在 `.env` / `.env.development` / `.env.production` 中配置。
4. CORS 采用 `allow_origins` 白名单且 `allow_credentials=False`（JWT 走请求头，不用 Cookie），避免浏览器拒绝 `*` 与凭据共存的组合。

## ⚠️ 已知限制

1. **AniNewsAPI 不可达时会自动降级到 RSS**。主源字段是按常见结构做容错映射的，未在真实响应上验证；若字段有出入，只需调整 `AniNewsAPIFetcher.FIELD_ALIASES`，无需改动工作流。
2. **备用 RSS 支持多源**（`NEWS_FALLBACK_RSS` 逗号分隔）。单个源条目数量有限（MyAnimeList news RSS 约 10 条），只配一个源会出现「抓完就没有新内容」—— 这正是「反复只看到同几条资讯」的原因。多源会先聚合全部源再按 `source_uid` 去重截断（不能取够 limit 就 break，否则第一个源会占满额度）。
3. **已入库条目默认不会再进流水线**。抓取阶段直接丢弃库中已有的 `source_uid`，避免重复翻译/摘要/审核浪费模型调用，也避免覆盖已发布内容。因此 `NEWS_FETCH_OVER_FETCH`（默认 3 倍）是拿到新内容的关键。
   例外：`repair=true` 时，正文残缺且未补全（`content_enriched=0`）的条目会被重新处理，
   见「正文修复」。前端「刷新」按钮已默认带 `repair=true`。
4. **备用 RSS 的正文需要补全**。MyAnimeList 的 RSS 只提供约 500 字摘要、Anime Corner 约 100 字，
   且都在词中间硬截断。因此抓取后会自动回到详情页抓全文（见「正文补全」），
   补全后正文可达 1500~2000 字。若某条目补全失败（网络异常、站点改版未适配），
   会保留 RSS 摘要原样入库，此时正文末尾的 `...` 属来源自身的截断。
   新增抓取源时，需在 `app/news/extractor.py` 的 `SITE_RULES` 里补一条容器规则，
   否则该站点不做补全（不会发无效请求）。
5. **翻译入参在句子边界截断**（上限 8000 字符，`TRANSLATE_PROMPT_LIMIT`）。直接按字符硬截断会导致译文末尾出现英文残缺——这一点已由审核 agent 在联调中真实检出（原因：「正文末尾出现英文残缺'composing th...'，翻译不完整」），因此改为优先回退到最近句末标点。
6. **封面图与正文依赖来源**。若来源未提供封面或全文，`coverImage` 为空、`content` 可能只有摘要（前端已对空封面做占位处理）。
7. **关联动漫为尽力而为**。仅当标题片段能在 `anime` 表命中时才写入 `related_anime_id`，否则留空（不写不存在的外键）。
8. **阅读量不自增**。避免爬虫/刷新刷量，如需统计建议在详情接口显式累加。
9. **工作流为同步阻塞**。单次运行包含多次模型调用，故手动触发走后台任务、定时任务独立线程；如需高并发建议改为队列消费。
10. **分类由翻译 agent 补齐**。RSS 源通常不带分类，因此由模型判定 + 关键词兜底归一化到「动画/漫画/声优/游戏/活动」，保证前端筛选标签始终有值。
