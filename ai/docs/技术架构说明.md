# 技术架构说明

## 📖 概述

本文档说明动漫AI问答服务的技术架构、模块划分与关键设计决策。

服务当前的技术底座：

| 维度 | 选型 |
|------|------|
| Web 框架 | FastAPI + Uvicorn |
| Agent 编排 | LangChain 1.x + LangGraph 1.x |
| 对话持久化 | LangGraph 检查点（`langgraph-checkpoint-postgres`） |
| 持久化数据库 | PostgreSQL（会话元数据 + 检查点） |
| 业务数据源 | MySQL（只读，归 Java 后端所有） |
| 大模型 | DeepSeek Chat（经 `langchain-openai` 调用） |
| 流式传输 | Server-Sent Events（SSE） |

> 本文档描述的是重构后的实现。接口契约与重构前完全一致，前端无需改动。

## 🔧 技术栈详解

### 1. 后端框架 - FastAPI

**版本**：FastAPI 0.115+，Uvicorn 0.30+

**选择理由**：
- 依赖注入（`Depends`）让服务装配与路由解耦，测试可整体替换
- Pydantic 请求校验 + 自动生成 OpenAPI 文档
- 异步原生，`StreamingResponse` 天然适配 SSE
- 全链路类型标注

**应用装配**：

```python
app = FastAPI(
    title="动漫AI问答系统",
    docs_url="/api/docs",
    redoc_url="/api/redoc",
    openapi_url="/api/openapi.json",
    lifespan=lifespan,
)

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.cors_origin_list,
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE", "OPTIONS"],
    allow_headers=["Content-Type", "Authorization"],
    max_age=3600,
)
```

**启动流程（lifespan）**：

```
MySQL 客户端初始化（惰性连接）
        ↓
PostgreSQL 同步连接池 + chat_sessions 建表（会话元数据）
        ↓
AsyncPostgresSaver 初始化（自建异步池 + 幂等建表）
        ↓
Agent 构建（绑定异步检查点）
        ↓
SessionService / ChatService / NewsService 装配 → 挂到 app.state
```

> 若 PostgreSQL 不可用，服务仍会启动（会话接口不可用并输出明确日志），这是刻意的降级设计。

**同步调用不阻塞事件循环**：数据库访问为同步 API，路由中统一经 `run_in_threadpool` 执行。

### 2. Agent 引擎 - LangChain + LangGraph

**LangChain 1.x**：模型抽象（`ChatOpenAI`）、消息类（`HumanMessage` / `AIMessage` / `ToolMessage`）、`@tool` 工具框架。

**LangGraph 1.x**：Agent 图编排（`create_agent`）、检查点持久化（`PostgresSaver`）、流式输出。

**模型初始化**：

```python
llm = ChatOpenAI(
    model=settings.llm_model,             # deepseek-chat
    api_key=settings.deepseek_api_key,
    base_url=settings.deepseek_api_url,   # https://api.deepseek.com/v1
    temperature=settings.llm_temperature, # 0.7
    max_tokens=settings.llm_max_tokens,   # 1000
)
```

**Agent 构建**：

```python
create_agent(
    llm,
    ANIME_TOOLS,
    system_prompt=SYSTEM_PROMPT,
    state_schema=AgentState,
    middleware=[MessageIdMiddleware()],
    checkpointer=postgres_saver,
)
```

**状态定义**（`app/agent/state.py`）：

```python
class AgentState(TypedDict, total=False):
    messages: Annotated[list[AnyMessage], add_messages]  # 对话历史
    user_id: int | None                                  # 当前用户，供工具查询
```

- `messages` 使用 `add_messages` 归约器：新消息追加、同 id 消息替换
- `user_id` 每轮注入并随检查点持久化，工具据此查询个人数据
- 对外暴露的 `message_id` 存放在各条 `AIMessage.additional_kwargs` 中

**两种 Agent 实例**：

| 场景 | 检查点 | 说明 |
|------|--------|------|
| 有会话 | `AsyncPostgresSaver` | 对话状态持久化到 PostgreSQL（异步接口） |
| 未登录（无 `user_id`） | `InMemorySaver` | LangGraph 绑定检查点后强制要求 `thread_id`，故用瞬时线程承载，不写库 |

### 4. 会话持久化 - PostgreSQL + LangGraph 检查点

**重构前的做法**：业务代码手工 `save_message()` 写入 MySQL 的 `chat_messages`，下一轮再把历史手工拼进 prompt。

**现在的做法**：把对话状态交给 LangGraph 检查点。

| 数据 | 存储位置 |
|------|----------|
| 对话状态与消息（HumanMessage / AIMessage / ToolMessage） | LangGraph 检查点表 |
| 会话元数据（标题、归属用户、软删除） | `chat_sessions` 表 |

**`session_id` 直接作为 `thread_id`**：

```python
config = {"configurable": {"thread_id": session_id}}
```

带来三个直接收益：

- **持久化记忆**：多轮对话由检查点自动恢复，无需手工拼装历史
- **结构化消息**：工具调用链天然保留在状态中
- **单一事实来源**：会话状态只有一处写入路径

**⚠️ 必须使用 AsyncPostgresSaver（不能用同步 PostgresSaver）**

FastAPI 路由是异步的，对话链路使用 `agent.astream()` / `agent.aget_state()`。
同步 `PostgresSaver` 未实现异步接口 —— `BaseCheckpointSaver.aget_tuple()`
的默认实现直接抛 `NotImplementedError`，会让**流式问答整体不可用**：

```
File "langgraph/checkpoint/base/__init__.py", line 441, in aget_tuple
    raise NotImplementedError
```

因此检查点基于 `AsyncPostgresSaver` + psycopg **异步**连接池：

```python
AsyncConnectionPool(
    conninfo=database_url,
    min_size=1,
    max_size=10,
    kwargs={"autocommit": True, "row_factory": dict_row},  # 硬性要求
    open=False,
)
```

由此带来的调用约定：

| 场景 | 可用接口 |
|------|----------|
| FastAPI 路由（生产） | **异步**：`aget_state` / `astream` |
| 离线脚本、单元测试 | 可用 `get_state`（同步），但生产不可 |

`SessionService` 因此同时提供 `get_messages_async()`（路由使用）与
`get_messages()`（仅离线/测试）。回归测试见 `tests/test_async_checkpointer.py`：
它用一个「只实现同步接口」的检查点替身模拟真实故障，任何误用都会在离线环境立即失败。

> 另注：会话元数据表 `chat_sessions` 与检查点是**两个独立的连接池**
> （元数据用同步池，检查点用异步池），互不影响。

**为什么会话元数据仍单独建表**：检查点只描述「对话状态」，不含标题、归属、软删除等业务语义。因此：

- `thread_id == session_id` 一一对应
- **会话存在性一律以元数据表为准**，而非检查点是否存在
  - 「刚创建但还没对话的空会话」也能被正确列出与访问
  - 软删除后自然视为不存在，语义与重构前一致

### 5. 流式传输 - Server-Sent Events (SSE)

**为什么用 SSE**：单向实时推送、比 WebSocket 简单、浏览器原生支持、自动重连。

**帧格式**：

```
data: {"success": true, "chunk": "文本片段", "type": "content"}

data: {"success": true, "chunk": "", "type": "end",
       "session_id": "session_xxx", "message_id": "msg_xxx"}
```

**事件类型**：

| `type` | 说明 |
|--------|------|
| `content` | 文本片段（含工具调用前的过渡语） |
| `thinking` | 进度提示（`stage=thinking` / `reasoning` / `tool`，`tool` 阶段带工具名），无正文 |
| `retract` | 兼容保留，当前不再发出 |
| `end` | 完成，携带 `session_id` 与 `message_id` |
| `error` | 出错或非动漫问题 |

**实现**（`app/core/sse.py` + `StreamingResponse`）：

```python
return StreamingResponse(stream, **sse.sse_response_kwargs())
# media_type=text/event-stream
# headers: Cache-Control=no-cache, X-Accel-Buffering=no, Connection=keep-alive
```

**逐 token 输出**：使用 `stream_mode="messages"`，LangGraph 产出逐 token 的 `AIMessageChunk`。前端是 `fullAnswer += chunk` 的累加渲染，因此逐字输出体验更好，且不改变任何响应字段。同名模式下也会混入 `ToolMessage` 与 reasoning，故必须经 `AnswerStreamFilter` 净化（见「app/services —— 业务层」）。

**MessageIdMiddleware —— 消息ID的产生方式**

```python
class MessageIdMiddleware(AgentMiddleware):
    def after_agent(self, state, runtime):
        updates = []
        for message in state.get("messages", []):
            if not isinstance(message, AIMessage):
                continue
            if not message.content or message.additional_kwargs.get("message_id"):
                continue
            updates.append(message.model_copy(update={
                "additional_kwargs": {
                    **message.additional_kwargs,
                    "message_id": new_message_id(),   # msg_ + 16位十六进制
                }
            }))
        return {"messages": updates} if updates else None
```

要点：
- 该字段随消息进入检查点，多轮对话不会重复生成
- 历史接口返回的 `message_id` 与当轮 `end` 事件的完全一致
- 用 `model_copy` 返回同 id 新消息交由 `add_messages` 替换，避免整表回写造成重复追加

**ContextSummaryMiddleware —— 摘要以 SystemMessage 入状态**

LangChain 自带的 `SummarizationMiddleware` 会把历史摘要包成 **HumanMessage**：

```python
HumanMessage(content=f"Here is a summary of the conversation to date:\n\n{summary}",
             additional_kwargs={"lc_source": "summarization"})
```

问题在于历史接口把 HumanMessage 当「用户发言」返回，前端就会冒出一条用户从没发过、
还是英文的假消息。因此这里只替换消息构造这一处：

```python
class ContextSummaryMiddleware(SummarizationMiddleware):
    @staticmethod
    def _build_new_messages(summary: str) -> list[SystemMessage]:
        return [SystemMessage(
            content=SUMMARY_MESSAGE_PREFIX + summary,
            additional_kwargs={"lc_source": SUMMARIZATION_SOURCE},
        )]
```

- 模型侧：system 角色本就是「背景设定」，比伪装成用户发言语义更准；
  实测 DeepSeek 接受列表中部的 system 消息并能正确使用摘要内容
- 展示侧：`_format_message()` 只映射 Human / AI，SystemMessage 天然不出现
- 双保险：除类型判断外，还按 `lc_source == "summarization"` 再挡一次，
  防止 LangChain 升级后改回 HumanMessage

**chat_service.py —— 一次问答的完整编排**

```
stream_answer(question, user_id, session_id)
        ↓
is_anime_related_question()  ──否──→ error 事件(is_anime_related=false) → 结束
        ↓ 是
_resolve_session()  有session_id→校验存在性；有user_id→建会话(标题=问题前20字)
        ↓
agent.astream(state, config, stream_mode="messages")
        ↓
AnswerStreamFilter.feed_with_step(chunk, langgraph_step)
        ├─ AIMessage 正文（含过渡语） → content 事件，逐块下发
        ├─ AIMessage 带 reasoning     → thinking(stage=reasoning)
        ├─ AIMessage 带 tool_calls    → tool 事件（带工具名）
        └─ ToolMessage                → thinking(stage=thinking)，内容不外发
        ↓
agent.aget_state(config) 取回 message_id
        ↓
end 事件（session_id + message_id）
```

**stream_filter.py —— 回答净化**

`stream_mode="messages"` 会把图上**所有节点**的消息块都吐出来，其中必须挡住的两类：`ToolMessage` 的原始 JSON、模型的 reasoning。而带 `tool_calls` 的 `AIMessage` 正文（「我来查询一下」）**不再**挡 —— 它是正常对话内容。

| 流出内容 | 处理 |
|------|------|
| `ToolMessage` | 不外发，改发 `thinking` |
| reasoning（`additional_kwargs` 或 reasoning 内容块） | 只发 `thinking(stage=reasoning)`，永不进正文 |
| `AIMessage` 正文（含带 `tool_calls` 的） | 逐块 `content` 下发 |
| `tool_calls` | `tool` 事件，每步每个工具一次 |

**没有 retract、没有缓冲**：过渡语发出去就留着，工具提示叠加在下，续写正文继续追加到同一气泡。`AIMessageChunk` 流式下工具名只出现在首个分片，因此按名字去重即可避免重复提示。

reasoning 的结构化来源有两个：`additional_kwargs["reasoning_content"]`（DeepSeek-R1 / `ChatDeepSeek`）与 `content` 块中的 `reasoning`/`thinking` 块（LC v1 `content_blocks`）。本项目 `ChatOpenAI` 走 chat-completions 时 `reasoning_content` 在 `_convert_delta_to_message_chunk` 就被丢弃，实测确认它不会污染 `content`；过滤器仍做结构化防御，换 provider 时规则自动生效。

配套：`message_answer_text()` 供历史接口取单条消息正文，`final_answer_from_messages()` 供非流式路径拼接全部正文。三者（流式 / 历史 / 非流式）规则一致，回归测试见 `tests/test_stream_filter.py` 与 `tests/test_stream_endpoint.py`。

**流式异常处理**

异常统一降级为 `error` 事件（HTTP 仍为 200），与重构前一致。

### 7. app/rag —— 知识库检索模块

| 文件 | 职责 |
|------|------|
| `embeddings.py` | 向量模型：优先 DashScope `text-embedding-v3`，无 key 时降级为本地 hash 向量 |
| `loaders.py` | 文档解析：txt / md / pdf / docx，统一切分为带元数据的 chunk |
| `store.py` | Chroma `PersistentClient` 封装：集合读写、删除、统计、**混合检索编排** |
| `keyword_index.py` | BM25 关键词索引（jieba 词 + 汉字二元组，随知识库版本失效重建） |
| `fusion.py` | RRF（Reciprocal Rank Fusion）融合多路检索结果 |
| `rerank.py` | 百炼 text-rerank 客户端（`gte-rerank-v2`） |
| `ingest.py` | 入库编排：解析 → 切分 → 向量化 → 写 Chroma |
| `tools.py` | `search_knowledge_base` 工具，供 Agent 在回答时检索 |

**检索管线（`KnowledgeStore.search`）**：

```
查询 ──┬─► 向量检索（候选池 20）─┐
       │                        ├─► RRF 融合 ─► 前 8 条 ─► 百炼重排 ─► top_k
       └─► BM25 检索（候选池 20）┘
```

设计要点：

- **向量库可插拔**：`build_embeddings()` 按配置与可用性选择后端，本地 hash 向量保证无网络时仍可跑通链路与测试
- **集合按 embedding 空间隔离**：Chroma 集合的维度在创建时固定，切换提供方（本地兜底 512 维 ↔ DashScope 1024 维）会直接报
  `Collection expecting embedding with dimension of 512, got 1024`。因此集合名带上 `provider + 模型/维度`：
  `anime_knowledge__dashscope_text_embedding_v3` / `anime_knowledge__local_hash_512`
- **旧集合自动迁移**：早期版本固定用 `anime_knowledge` 这个名字。切换到新空间时，若目标集合为空而旧集合有数据，
  会用**当前 embedding 重新向量化**后搬到新集合，成功写入后才删除旧集合（失败则保留，下次重试）
- **检索是工具而非前置步骤**：`search_knowledge_base` 与 Anime 工具同级注册到 `AGENT_TOOLS`，由模型自行决定是否检索，避免每轮都付出向量化开销
- **集合固定 cosine 距离**：`get_or_create_collection(metadata={"hnsw:space": "cosine"})`，相似度阈值才有稳定语义
- **运行时数据不进版本库**：`chroma_db/` 与 `knowledge/` 均被 gitignore

**混合检索与重排（本期新增）**

- **为什么要 BM25**：向量检索对**专有名词**（角色名、作品名）天生弱，BM25 按词频精确命中，两者互补。融合用 RRF：它只看**名次**，因此不需要对齐「余弦相似度 0-1」与「BM25 无上界分」这两种不同尺度
- **中文分词的坑**：jieba 词典外的专名会被切成单字（实测「村正」→「村」「正」），既丢区分度又引入「的」「是」这类单字噪声。因此分词器 = jieba 词 **+ 汉字二元组**（`绫弥`/`弥一`/`一条`/`村正`），不依赖词典兜住 OOV 专名
- **为什么重排走 API**：本地 `bge-reranker-v2-m3` 是 fp32 XLM-R large（2.1 GB 权重），要跑必须装 torch（约 2.6 GB），CPU 单次 1~3 秒；百炼 `gte-rerank-v2` 实测 0.3~1.2 秒、按 token 计费。**未用** community 的 `DashScopeRerank`：它把模型名硬编码为 `gte-rerank`（当前账号 403 AccessDenied），绕过要触碰其私有 `client`，且会拖入整个 `dashscope` SDK
- **分数语义**：`SearchHit.score` 在重排可用时是重排相关度（0-1，校准好）；重排关闭时是**真实余弦相似度**——用 Chroma 里已存的向量本地计算，零额外 embedding 请求。刻意不用 RRF 相对分展示，那会把「弱相关」显示成 0.97，误导模型
- **降级**：BM25 建索引失败 → 纯向量；重排接口失败 → 用融合顺序。任一路挂掉都不让检索整体不可用
- **实测耗时**（真实 API）：embedding ≈1.3s（既有开销）、BM25 ≈1ms、重排 0.3~1.2s。延迟敏感时可 `RAG_RERANK_ENABLED=False`，仍保留 BM25 收益且零额外延迟

### 8. app/mcp —— MCP 集成模块

| 文件 | 职责 |
|------|------|
| `stdio_client.py` | 最小 MCP 客户端：JSON-RPC over stdio，握手 / tools/list / tools/call，超时与自动重启 |
| `bilibili.py` | B站业务封装：启动命令解析、搜索、补详情、加权排序、链接拼装 |
| `tools.py` | `recommend_bilibili_videos`：暴露给 Agent 的 LangChain 工具 |

**为什么自己实现客户端**：官方做法是装 `langchain-mcp-adapters` / `mcp` SDK，但 dry-run 显示
它们会把 `langchain-core` 升到 1.6.x、并升级 `starlette`/`httpx`，与现有
LangGraph + uvicorn 组合冲突。因此主环境**零新增依赖**，只实现用到的三个方法。

**为什么服务端装在独立 venv**：`bilibili-cognitive-server` 依赖 `fastmcp`、
`faster-whisper`、`ctranslate2`、`onnxruntime`（数百 MB）。装进主环境必然引发版本冲突。
服务端在 `ai/.venv-mcp` 中运行，本应用只通过 stdio 管道与它通信。

**stdio 客户端的工程要点**：

| 问题 | 处理 |
|------|------|
| Windows 管道无法用 select 设超时 | stdout 读取放后台线程，主线程按请求 id 从队列取结果并带超时 |
| 服务端会插入无 id 的通知（日志/进度） | 按 `id` 过滤响应，通知直接丢弃 |
| stderr 可能写满管道导致子进程阻塞 | 独立线程持续排空 stderr，保留最近 40 行用于报错 |
| 子进程崩溃 | 下次调用前检测 `poll()`，自动重启并重新握手 |
| 进程泄漏 | 应用 lifespan 退出时 `shutdown_bilibili_service()` 回收 |

**B站工具调用成本控制**：搜索返回的条目只有播放量/弹幕，点赞等要再查详情。
因此按 `score = 播放×1 + 点赞×10 + 收藏×8 + 投币×6 + 弹幕×3 + 评论×2` 排序，
且只对播放量最高的前 `BILIBILI_DETAIL_LIMIT`（默认 10）条补详情。

## 🗄️ 数据库架构

### 表职责划分

| 表 | 所属 | 内容 | 创建方式 |
|----|------|------|----------|
| `chat_sessions` | 本服务 | 会话元数据（标题/用户/软删除） | 启动时幂等创建 |
| `checkpoints` | LangGraph | 每个检查点的状态快照 | `AsyncPostgresSaver.setup()` |
| `checkpoint_blobs` | LangGraph | 序列化后的通道数据（含消息） | `AsyncPostgresSaver.setup()` |
| `checkpoint_writes` | LangGraph | 中间写入结果 | `AsyncPostgresSaver.setup()` |
| `checkpoint_migrations` | LangGraph | 迁移版本记录 | `AsyncPostgresSaver.setup()` |

### chat_sessions 表结构

```sql
CREATE TABLE IF NOT EXISTS chat_sessions (
    session_id VARCHAR(64)  PRIMARY KEY,      -- 同时是 LangGraph thread_id
    user_id    BIGINT       NOT NULL,
    title      VARCHAR(255) NOT NULL DEFAULT '新会话',
    created_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_deleted SMALLINT     NOT NULL DEFAULT 0
);
```

### 索引

| 表 | 索引字段 | 目的 |
|----|---------|------|
| chat_sessions | session_id (PK) | 单会话查询 |
| chat_sessions | user_id | 用户会话列表 |
| chat_sessions | created_at | 时间范围查询 |

### 删除语义

| 操作 | 行为 |
|------|------|
| 软删除 `hard=false` | `is_deleted=1`，元数据与检查点均保留，接口视为不存在 |
| 硬删除 `hard=true` | 删除元数据行 + 按 `thread_id` 清理 `checkpoints` / `checkpoint_blobs` / `checkpoint_writes` |

### 与 MySQL 的关系

MySQL 仅作为**业务数据源**（`anime` / `user_anime` / `anime_character`），归 Java 后端所有，本服务只读：

```sql
SELECT ua.anime_id, a.title AS anime_title, ua.rating
FROM user_anime ua
LEFT JOIN anime a ON ua.anime_id = a.id
WHERE ua.user_id = %s AND ua.watch_status = 2
```

## 🔐 安全架构

### 1. SQL 注入防护

- 会话元数据与业务查询全部使用参数化查询

```python
# ✅ 正确
cursor.execute("SELECT * FROM chat_sessions WHERE session_id = %s", (session_id,))

# ❌ 错误
cursor.execute(f"SELECT * FROM chat_sessions WHERE session_id = '{session_id}'")
```

### 2. 凭据管理

- DeepSeek API Key、MySQL 口令、PostgreSQL 连接串全部经环境变量注入
- 代码中仅保留开发用默认值；`.env` 已在 `.gitignore` 中排除
- 兼容旧变量名：MySQL 侧同时接受 `DB_*` 与 `MYSQL_*`

### 3. CORS

由 `CORS_ORIGINS` 控制，默认 `*`；生产环境建议改为具体域名。

### 4. 访问控制（待实现）

当前接口未校验 JWT。前端已携带 `Authorization` 头，如需启用可仿照 Java 后端在 `app/core` 增加依赖校验。建议补充：

```python
async def require_auth(authorization: str = Header(None)) -> int:
    # 解析 Bearer Token → 返回 user_id
    ...
```

### 5. 数据隔离

会话访问严格基于 `session_id`，`user_id` 取自元数据表而非请求体，避免越权读写他人会话。

## 📊 性能优化

### 1. 连接池

PostgreSQL 连接池默认 `min_size=1, max_size=10`，经环境变量调整：

```
POSTGRES_POOL_MIN_SIZE=1
```

`GET /api/session/{id}/messages` 单次从检查点最多读取 1000 条，再按 `limit` 截取最近若干条，避免超长会话一次性加载。

会话状态由检查点承载，无需额外缓存层，减少一个部署依赖。
